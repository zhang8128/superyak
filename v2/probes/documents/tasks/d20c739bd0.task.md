A flood of sign-in attempts from the public internet should never lock out people signing in over the tailnet or from a browser we already know, so I'd like sign-ins split into three lanes, each with its own limit. Public sign-ins go two at a time with up to eight more waiting. Tailnet sign-ins go one at a time with four waiting, and a public request never goes into that lane. A public sign-in from a known browser, meaning one that presents a remembered-device token still valid for the username it is signing in as, goes into a third lane, also one at a time with four waiting.

Pick the lane before the request waits for a place. The check of the device token for that choice should only read and write nothing, and the sign-in itself should go on checking the token again as it does now. The whole sign-in should be done on threads set aside for its own lane, within that lane's limit, so that it neither holds up the server's handling of other requests nor takes threads the other routes rely on. The demo-account sign-in goes through the same lanes.

When every place in a lane, in progress and waiting, is taken, a new sign-in for it should be refused immediately with a 429 and an answer that says why. A refused attempt must not hash the password and must not count towards any failed-attempt limit. So while the public lane is full, a known browser's public sign-in and a tailnet sign-in both still succeed, and the attempts that were waiting still get their usual answers once their turn comes, leaving the lane empty afterwards.
