We want one peer's ship to be able to ask another peer's lighthouse to recall or read memories for it, a remote memory request. Before any route can carry one, we need what goes over the wire: the request with its signature, a check that a request is well formed, the answering peer's reply with its own signature, and the asking side's check of that reply.

The lighthouse message a request carries is the lighthouse protocol's own recall or read, under release 0.1 of that protocol, and 0.2 is refused. The peer has to check it itself, because it cannot use the lighthouse's code. Each sort carries only what it takes: a result, a message missing anything it needs, or one carrying what belongs to the other sort is refused, and so is a lighthouse message given as plain text. Both sorts say who the memories are for, who publishes them and the reason for asking, each 1 to 256 characters. Use valid existing lighthouse scopes; names and segments are each 1 to 512 characters, and inconsistent or surplus scope information is refused. A recall must be for the asker alone, never for wider sharing; its search text is 1 to 4,096 characters; the number of results wanted is a true whole number from 1 to 20, not 2.0 and not a yes or no; and its time is given as text of 1 to 64 characters, not a number. A read names the turn it belongs to in 1 to 64 characters, and from 1 to 5 different memories, each named by text of 1 to 128 characters, with no repeats.

Please add a check that says yes only to a well-formed remote memory request, with nothing missing and nothing extra, and no to anything else, including the fetch request a peer already sends to collect what waits for it, or a message a session sends on the memory route, offered in its place. Beyond its lighthouse message, a request must be format 1, as the whole number 1, not a yes or no, not 2 and not the text 1, and must declare itself a remote memory request, not a fetch request and not an answer. It carries a one-time value of 32 lowercase hex characters, is timestamped as a whole number rather than a fraction, text or a yes-or-no value, waits for a reply at most a whole number of milliseconds from 100 to 10,000 inclusive, and carries a signature of up to 128 characters of text. The asking peer and the answering peer are each named by their existing 64-character lowercase hex id. The installation it is meant for uses its existing UUID form, lowercase with its hyphens. The ship the memories are for and the ship whose memories they are are each named as on a card, by 1 to 64 letters, digits, underscores or dashes.

A peer signs only a complete remote memory request that it is itself asking, the same way and with the same key it signs fetch requests, so that the signature covers every other part, and it refuses to sign one asked by another peer or declaring another type. The answering peer accepts a request only when it is complete with nothing extra, declares itself a remote memory request, comes from the peer whose card it is checked against, and its signature verifies under that card's key. Anything else, such as a check against another peer's card or a request with any part changed after signing, the installation, the waiting time or the lighthouse message among them, is refused with status 403, exactly as a bad fetch request is refused. A fetch request never passes as a remote memory request, a remote memory request never passes as a fetch request, and an answer passes as neither. The three types, a fetch request, a remote memory request and its answer, are reserved: no record type may be any of them, and a peer refuses to sign a record of the answer's type.

A request's hash is the SHA-256, in hex, of the request together with its signature, in the same stable JSON form used for signing. The answering peer signs its answer the same way, and only a complete answer that it is itself giving; it refuses one given by another peer. The asking side checks an answer against the card it dialled, its own identity, the request's hash and one-time value, and the sort of lighthouse message it sent. It accepts the answer only when its signature verifies under the dialled card's key, it comes from the dialled peer and is addressed to the asker, it declares itself an answer in format 1, it carries that hash and that one-time value, and, with nothing extra, it holds under release 0.1 the results of the same sort of lighthouse message that was sent, together with a receipt of 1 to 256 characters for what was handed over. It refuses anything else: a tampered signature, another hash or one-time value, an answer from a peer other than the dialled one or addressed to someone else, an extra part, a read's results for a recall, a missing or empty receipt, a failure report in place of results, another type, another format number, or an answer whose signature is another peer's.
