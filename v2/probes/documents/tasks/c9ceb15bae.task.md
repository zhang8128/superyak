Some peers can't be reached from outside, so they must fetch waiting traffic from a reachable listener, and that starts with their card and with a signed request to fetch. Please add a second version of the peer card that marks a peer as one that initiates those fetches itself; such a card has no network address. There is no second-version card for a peer that is reached by its address: a second-version card that has an address, or that does not mark its peer as one that fetches, is rejected the way an invalid card is rejected today, and so are a first-version card that carries that mark, whatever it says, or that has no address, a third-version card, and a version given as true rather than a number. First-version cards are checked exactly as they are today.

When a peer builds its own card, being reached by its address stays the default, and the first-version card it builds must be byte for byte the one it builds today. Asked for a card for a peer that fetches, it builds the second version with no address. Asked for one that fetches but given an address, or one reached by its address but given none, it rejects the card as invalid, and asking for any other way of being reached is an error. The pairing code of a second-version card covers the whole card, so it changes when the key and the peer's id change or when the person on the card changes, and it differs from the code of the same peer's first-version card.

A peer should sign its own fetch request with its Ed25519 key, the same way it signs the packets peers send each other and its records, so that the signing covers every part of the request. It should refuse to sign anything but a complete fetch request of its own: nothing missing and nothing extra, marked as a fetch request, and naming itself as the asking peer. Checking a fetch request against a card should accept it only when it is complete with nothing extra, is marked as a fetch request, names the card's peer as the asking peer, and its signing verifies under the card's key. Anything else, including any part changed after signing or a check against another peer's card, is rejected with status 403 and an explanation.

Because all three are signed the same way by the same key, a fetch request, a signed packet and a signed record must never pass as one another: a packet is not accepted as a fetch request, a fetch request is not accepted as a packet, a fetch request is not accepted as a record, and the mark that makes a request a fetch request is reserved so that no record type may take it.

Finally, the strict JSON reader keeps the 6 MiB cap that packets have today as its default and rejects anything larger with status 413, but it lets a caller name its own cap, larger for the reply to a fetch or smaller, and it enforces the cap named.
