Now the pulling side needs its half: a peer that federates by pulling should be able to make one pull from a listener whose card it holds. Each request is signed, with a fresh one-time challenge (a different one for every request) and the current time, asks for up to 20 signed deliveries and up to 1 MiB of response, and carries what the peer owes that listener, at most 100 acknowledgements and 100 rejections. What it owes stays in memory until a pull that carries it succeeds, so a failed pull loses none, and once carried it is not carried again.

Hand each signed delivery that comes to the peer's normal receiving path. One accepted, or one already seen before, is acknowledged, and the listener then marks its row delivered. When receiving turns one down with a 4xx about that row, such as an unknown participant, report it rejected with that status, so the listener marks it and the following row still comes through. A reply about the peer as a whole (401, 404, 408, 421, 425, 429, or a 403 about the peer itself, such as failed authentication), a 5xx or a local fault is neither acknowledged nor reported, so the row stays waiting. A signed delivery that comes from another peer is discarded and logged, never handed to the receiving path. One that won't parse still goes to the receiving path, and it is neither acknowledged nor reported as a row rejection.

Keep asking in successive requests while the listener says there is traffic still waiting, at most 10 such requests in one pull. Stop early when a response brought signed deliveries but none gave a new acknowledgement or rejection; an empty response with traffic still waiting goes on. Then, if anything is still owed, make one last request asking for no signed deliveries, to carry it. The following pull is normally in 60 seconds; after 10 requests with traffic still waiting, it goes at once. Three hundred stale rows ahead of a live one must all clear in one pull, in two requests for deliveries, the 300 withdrawn and the live one delivered, and the pull's own requests never met with a 409.

Replies to the pull itself: when the listener says it is already serving this peer, ask again after 5 seconds with a new one-time challenge, and if it says so a second time, wait for the following pull in 60 seconds; when it says it has already seen the request's one-time challenge, ask again at once, once, and a second time wait for the following pull in 60 seconds. Neither is a failure. A 403 isn't one either: keep its status and reason on the peer's delivery record as its latest problem, pull again in 60 seconds, and flag a warning when the listener turned the pull down because the request's time was over 300 seconds off its own. A 404 means the listener has no pull route: wait 5 minutes and leave the peer's delivery record untouched. A 400 or other 4xx is logged as a bug on one side, waits 60 seconds and keeps the acknowledgements for the following pull. Anything else, including 401, 408, 421, 425, 429, a 5xx, a stall, a lost connection, a certificate pin mismatch or a malformed response, is a peer failure: count it, note when failing began and the problem, and back off 2 seconds after the first, doubling, capped at 300 seconds. Apply the same response validation over the network and in process; an error from an in-process sender counts as the reply the network would give, with the same status and reason.

A successful pull clears the peer's failure state and records when it last succeeded, so a push backoff never holds back a pull and pushes go again at once. Report the pull's progress, the problems it met and when it will try again.
