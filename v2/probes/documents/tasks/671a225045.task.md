A peer that federates by pulling calls its listener and asks for what is waiting for it. Please make the listener answer such a pull. It hands back the signed deliveries waiting for the peer that asked, byte for byte what a push would send, and says whether there is traffic still waiting for that peer beyond what it handed back, counting only that peer's rows. An initially pending row stays pending until the puller acknowledges it in a later pull, which marks it delivered, so a lost response costs one duplicate at the receiver. A pull may also report events the puller rejected, each with a code from 400 to 499: the row is marked as rejected, the code kept as the reason it failed, the rest of the row left alone. Acknowledgements and rejections touch only the asking peer's own rows, and only rows still pending or failed. A pull asks for zero to twenty signed deliveries; zero only applies its acknowledgements and rejections.

Check each request in this order, and turn it down with a reason at the first check it fails. First its form, as a bad request: no field missing and none extra, version 1, both peer ids 64 lowercase hex, a one-time challenge of 32 lowercase hex, a request time supplied as an integer number of seconds, not a boolean or decimal number, a count that is a true integer from 0 to 20, a byte allowance from 64 KiB to the 6 MiB maximum for one signed delivery, at most 100 acknowledgements and 100 rejections with ids of 32 lowercase hex and rejection codes from 400 to 499, a signature of at most 128 characters; a signed delivery or any other record sent in place of a pull fails. Then, as forbidden: a request addressed to another peer, before any one-time challenge is stored; an asking peer not paired, or paired but delivering by push; a bad signature; a request time over 300 seconds away from the listener's own time. Then, as a conflict, a one-time challenge already seen from that asking peer: it is stored before the next check and kept while a copy of the request could still pass the time check, dropped only once the request's own time is over 600 seconds behind the listener's. Last, one pull per peer at a time: a second valid one while the first still runs is turned down as a conflict, saying why, and a forged one meanwhile is turned down on its signature, never for the overlap.

A verified pull records when that peer last pulled, clears its failure backoff, and brings the queue up to date so anything just shared is included. Then walk only that peer's waiting rows, in queue order, at most 200 rows for about 5 seconds, stopping at the count asked for or at the byte allowance; a signed delivery that would go past the allowance waits for the next pull unless it is the first, so one over the allowance goes only alone. A whole response may be at most 6 MiB plus 64 KiB, with 1 KiB of that kept for framing. Each row is prepared in its own short unit of database work under the delivery lock, never one held across rows, and that same unit writes its mark: a row no longer current is withdrawn; one whose signed delivery could not fit in a response alone is rejected where it waits, with code 413 and a reason; a local fault rejects that row and the walk goes on; a database lock error leaves the row as it was. Each signed delivery handed back adds one to its row's count of tries. Other peers' rows, a push peer's included, are never touched.
