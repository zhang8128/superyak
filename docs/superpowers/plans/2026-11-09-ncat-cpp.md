# The n-category in C++: plan and scalability analysis

Defiant, 2026-11-09, for Andy. **Status: a draft.** No reviewer has read it, and nothing in it is built. Andy's two
decisions in section 2 come first. Under station law, a fresh reviewer approves the spec each phase writes (section 3).
Tardis builds the kernel and Rio Grande the store, as they split the work on 2026-11-07. Every branch merges under
section 2.

**Goal:** an n-category for Engram's memory that is actually an n-category: composition is defined wherever its laws
say it should be, and every law holds. It is written in C++20, survives crashes and hostile input, and costs grow
with how much it is used, not with what is possible.

**Starting point:** Tardis's kernel, `engram/ncat_kernel.c` on `tardis/ncat-kernel` (40b27d5e, spec revision 3,
approved), and Rio Grande's store on it, which is on the Pi only.

**Tech stack:** C++20 behind the kernel's existing narrow `extern "C"` ABI, `ctypes` from Python (unchanged), and SQLite
for the store. No new runtime dependencies.

**Notation used throughout:**

| Symbol | Meaning |
|---|---|
| E | the elements of a cell's shape. A path of L steps has E = 2L + 1 |
| W | the words that store a cell: 4 per element plus one per face, so O(E + faces) |
| n | dimension (the kernel allows up to 15) |
| w | front width: the largest boundary slice the canonical walk sweeps (for a 2-cell, the wires in its widest slice) |
| T | the top-dimensional elements of a cell |
| g | the largest generator's shape size |
| N | cells held in one category, or rows in the store |
| L | a session's length, in steps |

## 1. Where it stands

- **On main, nothing is an n-category.** The audit on issue #2 found arrows between memories, plus unchecked
  "2-cells" that are off by default.
- **The kernel on `tardis/ncat-kernel`** is the loop-free fragment of the free strict n-category on a regular
  polygraph:
  - **Up to n = 2 it is exact and total.** That is the free strict 2-category.
  - **From n = 3 composition is partial.** Shapes that aren't loop-free are refused (-5). That includes some cells
    whose shape does determine them (n = 3) and real torsion (n = 4).
  - **Generators** with identity boundaries (-2) or non-round boundaries (-4) are refused.
  - **A traversal that can't finish** has its own error code (-8). It has never been hit, and nothing proves it can't
    happen.
- **The evidence is all synthetic.** 1.3 million pairs of cells, up to n = 4, agreed with Rio Grande's separate
  engine. The independent `rewalt` cross-check never ran, because installing it was refused on Tardis.
- **The store** runs on the Pi only: Python on SQLite, measured on synthetic data (section 7).
- **Use:** the store has 16 recall rows, 2 of them used. Both outside reads parked new building until recall shows
  real use. Andy has since said more will be built on it, and that the C++ is for that.

## 2. Andy's decisions, first

**D1. What a cell is, above dimension 2.** Both options have the same cells and laws through n = 2. They differ from n = 3.

- **F, the free strict n-category.** This is what the kernel aims at today.
  - It is exact where it answers, but composition stays partial: it refuses shapes it can't decide.
  - Equality in the free strict ω-category is decidable in general (Makkai). I found no efficient general algorithm
    in the sources I checked.
  - Torsion appears from dimension 4. That is Rio Grande's example on issue #2, "torsion" in Forest's sense.
- **Q, labelled regular molecules up to isomorphism.** Composition is total, and every law holds strictly, because
  molecules have no automorphisms.
  - Equality is isomorphism of labelled regular molecules. That is polynomial at every dimension: Hadzihasanovic and
    Kessler give a canonical form in O(E³ log E), and a later talk of theirs says O(E² log E).
  - Q agrees with F on every loop-free shape (Steiner's theorem). That covers all of n ≤ 2 and the cases the kernel
    already accepts.
  - Beyond those shapes, Q makes independent rewrites commute. It identifies torsion cells that F would tell apart.
- **Recommendation: Q.**
  - For memory, a 2-cell says "this route can replace that one without costing more", and a 3-cell compares two such
    replacements. Two independent improvements in different places giving the same result in either order is the
    meaning we want.
  - Torsion at n ≥ 4 records the order of independent comparisons of comparisons, which memory never needs.
  - A `free_certified` flag (the loop-free check) still says, per cell, whether Q's answer is also F's.
- **This needs a mathematician's check.** That Q is a strict n-category is Rio Grande's reading on issue #2
  (2026-11-07) and my reading of Hadzihasanovic's framework. Phase 3's fresh reviewer confirms or refutes it before
  anything relies on it.

**D2. When to port.** Rio Grande proposes porting the 817 lines when the next native piece starts.
- Andy has said more will be built, and every phase below is native code, so **I recommend porting now, as phase 1.**
- It's about a day of agent work, and the existing tests become its oracle.

**D3 (Andy's to weigh).** The outside reads asked for use before more structure.
- This plan runs phase 6's instrumentation alongside phase 2.
- It holds phase 5 (crossing between lighthouses) until real use has been shown.

## 3. What today's kernel costs

Derived from the code (`ncat_kernel.c`, 40b27d5e), then measured.

| Operation | Cost | Why |
|---|---|---|
| Equality of held cells | **O(1)** | cells are interned to integers |
| Intern a cell | O(W) expected | hash, probe at load ≤ ½, compare on a hit. Worst case O(N) per probe when hashes collide |
| Boundary ∂ₖ±, first time | O(W) + canon(∂) | copies the cell, collects the boundary, canonicalises it. Then O(1) from the memo |
| Compose a ∘ₖ b | O(W_a + W_b) + canon(a ∘ₖ b) + loop_free | plus two boundary canonicalisations every time, since `boundary_ordered` isn't memoized |
| canon, n = 1 (paths) | O(E) | one pass |
| canon, n = 2 | O(T · w) ≤ O(E²) | each top element re-walks the current front |
| canon, n general | O(E · w^(n−1)), worst O(E^n) | the walk recurses once per dimension, and each step re-walks the front below it (an upper bound read from the code, not proved tight) |
| loop_free (n ≥ 3 only) | O(n · E · g), worst O(n · E²) | the closure of every element, once per dimension, then a topological sort |
| New generator | O(n · W) + loop_free + canon | roundness is checked at every dimension |
| A session built one step at a time | **O(L²) time and O(L²) memory** | each prefix is canonicalised whole, and every prefix stays held |
| Memory overall | O(every cell ever made) | nothing is freed until the category is; the 1 GiB budget refuses past that |
| Concurrency | one call at a time per category | one lock per category in Python, and scratch space shared per category |

**Measured on Defiant** (bazzite, x86-64, 16 threads, through Python `ctypes`). Every run was capped at 1 GB, and the
kernel's budget was 256 MB. The exponent is the log-log slope.

| Benchmark | Sizes | Result | Exponent | Predicted |
|---|---|---|---|---|
| A. One more step on a held path | L = 200 → 12,800 | 19 µs → 1.13 ms (about 88 ns per element) | **0.97** | 1 |
| B. A path built one step at a time | L = 250 → 2,000 | 3.9 → 222 ms; 1.7 → **97 MB held** | **1.96, and 1.96 for memory** | 2, 2 |
| C. The same path built by halving | L = 250 → 2,000 | 0.8 → 5.2 ms; 0.1 → 0.9 MB | **0.93, and 0.95 for memory** | 1 (L log L) |
| D. One more operation on a 2-cell tree | w = 26 → 201 | 34 → 554 µs | **1.38** | ≤ 2 (T ≈ w here) |
| E. One more mark on a 3-cell stack | E = 63 → 243 | 34 → 371 µs | **about 1.8** (first point dropped as warm-up) | between 1 and 2 |
| F. Equality, two 1,000-step paths built opposite ways | | 65 ns, mostly the Python call | | O(1) |
| G. Memory per 1-cell generator | 100,000 | 187 B held; 464,000 created per second | | |
| H. A 50-step session built by halving | 2,000 sessions | **26.9 KiB held each** with intermediates (about 2.4 KiB for the finished cell); 3,050 per second | | |

B against C is the headline. Same cell, but 43 times slower and 108 times the memory when built one step at a time,
and the gap grows linearly with L. That is the reviewer's 44.6 s and 4.3 GB at 1,000 steps of a 2-cell tree: O(L³) for
a tree whose front grows.

## 4. What breaks at scale, in order

1. **Building step by step is quadratic, in both time and memory (B).** Sessions arrive one use at a time, so this is
   the normal case, not a corner case.
2. **Nothing is ever freed (G, H).** Intermediates cost about 11 times the finished cell (H), and the budget's only
   answer is to refuse.
3. **Cell ids are local to one process.** They mean nothing to another process, a restart, or another lighthouse.
4. **One call at a time per category.** Composition gets no use of the other cores.
5. **canon's cost grows with dimension: O(E · w^(n−1)).** Thin cells make it cheap, but a wide 3- or 4-cell can cost
   E³ or E⁴. Hadzihasanovic and Kessler's canonical form is polynomial at every dimension.
6. **Partial composition from n = 3 (D1).** A caller can never be sure a composite exists.
7. **Interning's worst case is O(N) per probe.** The table's expected O(1) should hold for any input, including
   cells imported from other lighthouses.
8. **The store's durability.** The benchmark's `synchronous=NORMAL` can lose the most recent commits in a power cut.
   On main, retiring a memory leaves its arrows active, and a merge can bring a retired cell back (issue #2 audit).

None of 1 to 4, 7 or 8 is mathematics. They are implementation choices, and each has a standard fix. Only 5 and 6
touch the mathematics, and D1's option Q addresses both.

## 5. The C++ design

**Same ABI, new inside.** The `extern "C"` calls and error codes stay as they are, so `ncat.py`, its tests and Rio
Grande's store don't change. Every ABI function is `noexcept` and catches everything at the boundary. No exception
ever reaches `ctypes`.

**Cells.** A cell is immutable once made. It is stored in compressed sparse rows: per-element dimension and label,
face offsets, then input faces and output faces, each list sorted. Its 32-bit id is used inside the process. Its
256-bit content digest is its name outside the process. It is SHA-256 from a small implementation kept in the
source, so the kernel gains no dependency:
digest = H(canonical-form version ‖ formal dimension ‖ canonical words).

**Interning.** A sharded hash table with a seeded hash. Readers never take a lock, because cells don't change once
published. Writers lock only their shard.

**Memory.** Cells carry reference counts. Python handles and the store hold references, and memo entries are weak, so
intermediates die when nothing uses them. Memory becomes O(live cells), still under the byte budget. Reclamation
waits for an epoch, so a concurrent reader never sees a freed cell.

**Building cells:**
- `compose_many(cells[], k)` builds one shape and canonicalises it once, at O(canon(ΣE)), instead of once per prefix.
- A builder (`builder_new`, `push`, `finish`) does the same for a session that arrives one use at a time: a push is
  O(W of what it adds), and `finish` canonicalises once.
- For n = 1, canonical words are a concatenation, so a path's digest can also be kept rolling, for O(1) checks while
  a session is open.

**Boundaries come from the parts.** By globularity, ∂ⱼ±(a ∘ₖ b) for j < k is ∂ⱼ± a, which equals ∂ⱼ± b. For j = k
it is ∂ₖ⁻ a or ∂ₖ⁺ b. Both are O(1). For j > k it is ∂ⱼ a ∘ₖ ∂ⱼ b, memoized. The boundary's element order is read off
the canonical words, which are already in canonical order. That removes the two extra canonicalisations in every
compose.

**Canonical form (phase 3, under Q).** One algorithm for every regular molecule: Hadzihasanovic and Kessler's
traversal, which their paper bounds at O(E³ log E).
- Today's walk stays as a fast path only if it is proved to give the same words wherever it finishes. Otherwise it goes.
- Two canonical forms could never be allowed to disagree, since interning depends on there being one.
- -5 becomes the `free_certified` flag, computed lazily in O(n · E · g).
- -8 must become unreachable, shown by proof or by an exhaustive search up to a stated size.

**Concurrency.** Scratch space moves into each thread (`thread_local`), and the per-category lock goes. Independent
compositions then run in parallel, and the GIL is already released during each call.

**Hostile input.** The byte and step budgets stay.
- Every imported cell is checked against the molecule axioms and for round atoms before it is interned. That check
  is O(n · W).
- The ABI gets a libFuzzer harness, with the Python reference as its differential oracle.
- ASan, UBSan and TSan run in CI.

**Build.** `ncat.py` compiles with `/usr/bin/c++ -std=c++20 -O2 -fPIC -shared` plus today's hardening flags. g++ 12 on
the Pi covers what this needs (Rio Grande checked). Avoid `std::format`. Use a small result type, or `std::expected`
where every compiler has it.

## 6. Target costs

| Operation | Today | After the C++ plan |
|---|---|---|
| Equality | O(1) | O(1); between processes and machines, a digest compare |
| Session of L steps, arriving one use at a time | O(L²) time, O(L²) memory | **O(L) time, O(L) memory** |
| Compose a ∘ₖ b | O(W_a + W_b) + 3 canons + loop_free | O(W_a + W_b) + 1 canon (loop_free only when asked) |
| canon, any n | O(E · w^(n−1)), worst O(E^n); partial from n = 3 | O(E · w) fast path where it applies; **at worst O(E³ log E) for every n, and total** |
| Boundary of a composite, j ≤ k | canon of the boundary | **O(1)** |
| Memory | every cell ever made | **live cells only** |
| Independent compositions on c cores | 1 at a time | about c at a time |
| Interning, worst case | O(N) per probe | O(1) expected for any input (seeded hash) |

## 7. Scalability analysis

**The rule that makes it scale.** Rio Grande's store keeps generators and the composites actually used (sessions,
rails), each once by content.
- The closure, every composite that could exist, is exponential, even for a small graph. It is never computed.
- So the store's size is linear in use: generators plus the sizes of the used composites.
- Each kernel operation costs according to the cells it touches, not the size of the store. Only store lookups grow
  with N, and only as log N.

**Projection for one lighthouse:** 10⁶ memories, 10⁷ use-arrows (1-cell generators), 10⁶ sessions of 50 steps and 10⁴
rails (2-cells). The numbers come from G, H and Rio Grande's Pi measurements.

| Resource | Today's kernel | After the plan |
|---|---|---|
| Kernel memory, everything resident | arrows 1.9 GB + sessions **27 GB** with intermediates (2.4 GB without) | a bounded cache: the working set, say the last 10⁴ sessions, in tens of MB |
| Store on disk | about 29 B per generator row (35 MB for 1.2M) ⇒ about 300 MB for the arrows | the same, with sessions stored as generator sequences (about 200 B each, about 200 MB), canonicalised when read |
| Building all 10⁶ sessions | 5.5 min through Python one session at a time (H); quadratic if built step by step | about 9 µs each in one compose call (A's 88 ns × 101 elements) ⇒ about 9 s on one core |
| A durable write | 37 µs with NORMAL (about 27,000 a second) | FULL with group commit: an fsync per batch, not per row. Agents write far below either rate |
| Neighbours of a memory | 23 µs at 1.2M rows (Pi), O(log N + degree) | about one more B-tree level at 10⁷: tens of µs |
| Equality and boundary | O(1) | O(1) |

**What bounds it after the plan:**
- **Cell width, not store size.** Memory's cells are thin: sessions are paths (n = 1), and rails are small 2-cells.
  So E and w stay in the tens to hundreds, and canonicalising takes microseconds. A wide, high-dimensional cell would
  cost up to O(E³ log E), with the budget as the guard.
- **Single-writer SQLite per store.** Agent usage comes nowhere near it. A store that ever does gets sharded by
  lighthouse, which the federation already implies.

**What will bite later, beyond the kernel:**
- **Finding where a rail applies (subdiagram matching).** It takes linear time in the Hasse diagram for dimension ≤ 3,
  is in NP for every fixed dimension, and is an open question at 4 (Hadzihasanovic and Kessler, LICS 2023). **Keep
  rails at dimension 3 or below.**
- **Routing.** A* on the 1-skeleton costs O(A + V log V) per query in the worst case, less with a consistent
  heuristic (Proposition 1 on issue #2). Exact shortcut methods need shortcuts of equal cost (kernel spec, "Where
  speed comes from").
- **Sheaf cohomology.** H⁰ and H¹ over a cover need sparse linear algebra, O(nnz · k) per iteration. Dense
  decompositions are O(m³) and won't scale. Keep stalks small.
- **Between lighthouses.** Reconciling digest sets costs O(d log N) for d differing cells, which suits cells that
  never change.

## 8. Resilience

- **Crash.** The kernel is a cache. Everything rebuilds from the store by digest, deterministically. Every read checks
  its digest, so corruption shows up instead of spreading.
- **Power cut.** Use WAL with `synchronous=FULL` and group commits, or NORMAL with a stated loss window. Fault-injection
  tests kill writes with kill -9 and simulate torn pages.
- **Retirement.** The set of active cells stays closed under boundaries, so no active cell has a retired face. A merge
  can't resurrect a retired cell. These are the two bugs the audit found on main.
- **Hostile or broken input.** Imports are validated, budgets apply to every call, and the importer is fuzzed. A
  refusal changes nothing, as today.
- **Several machines.** Cells never change and are named by content, so a lighthouse's store is a grow-only set.
  Syncing two is a set union under permissions-core, and two lighthouses never conflict over a cell. Retirement is a
  separate, signed layer.
- **Backup and restore.** The station's backup covers the store, and a restore drill is part of phase 4's gate.

## 9. Phases

The order is 1, then 2 (with 6's instrumentation alongside), then 3, 4 and 5. Each phase is a branch with its own gate.

### Phase 1: the C++20 port, same behaviour (Tardis; about a day, plus a reader)

- [ ] Port `ncat_kernel.c` to C++20 behind the same ABI and error codes, with RAII for every buffer.
- [ ] Produce the same canonical words, byte for byte. Run the 172 tests, the `cross4` corpora and the mutants
  against both builds, and compare the words.
- [ ] Run clean under ASan and UBSan, and under TSan on the thread test.
- [ ] `ncat.py` builds with `c++ -std=c++20`.
- **Gate:** identical words and refusals on every corpus, and benchmarks A to F within 20% of today's.

### Phase 2: scale, same semantics (Tardis; Rio Grande reads)

- [ ] `compose_many` and the builder. **Gate:** a session built one use at a time has exponent ≤ 1.1 at B's sizes.
- [ ] Boundaries of composites from their parts, and boundary order from the canonical words. **Gate:** one canon
  per compose.
- [ ] Reference-counted cells and weak memo entries. **Gate:** a 50-step session holds about 2.4 KiB, and memory's
  exponent is ≤ 1.1.
- [ ] A seeded in-memory hash, and a 256-bit digest per cell.
- [ ] Scratch space per thread, a sharded intern table, and reads with no lock. **Gate:** with independent work, 8
  threads give at least 6 times the throughput of 1.
- [ ] Benchmarks A to H become CI tests that assert the fitted exponents.

### Phase 3: total composition, if D1 is Q (Tardis writes the spec and builds; a fresh math reviewer)

- [ ] Spec: the strict n-category of labelled regular molecules up to isomorphism. It says what Q identifies, gives
  the proof that the laws hold, and shows agreement with F on loop-free shapes.
- [ ] Canonical form for every regular molecule (Hadzihasanovic–Kessler), as the only canonical form.
- [ ] -5 becomes `free_certified`, and -8 is shown unreachable.
- [ ] The canonical-form version goes into the digest, with a migration that re-canonicalises stored cells.
- [ ] Cross-check with `rewalt` at n ≤ 4. Installing it needs Andy's yes.
- **Gate:** the reviewer's approval; 0 disagreements with `rewalt`, and with Rio Grande's reference on loop-free
  shapes; every law property-tested up to n = 5 with no refusals.

### Phase 4: the store, resilient (Rio Grande)

- [ ] Cells addressed by digest, and generator labels that are unique across lighthouses (lighthouse id plus a
  counter).
- [ ] Sessions stored as generator sequences.
- [ ] Durability as in section 8, with fault injection, and a digest check on every read.
- [ ] Retirement closed under boundaries, with no resurrection on merge.
- [ ] The kernel as a bounded cache with LRU residency, and rehydration on demand.
- [ ] Indices by boundary digest, so "what can follow this cell" is O(log N + out).
- **Gate:** the crash-consistency suite; a restore drill; a 10⁷-generator synthetic load on the Pi inside its memory
  budget.

### Phase 5: across lighthouses (Rio Grande and Tardis, under permissions-core; held until phase 6 shows use)

- [ ] Grow-only sync by digest-set reconciliation, of only what policy allows.
- [ ] Validation and fuzzing of every imported cell.
- **Gate:** the Pi and Tardis compose across a shared boundary, and fuzzing runs clean for a stated number of CPU hours.

### Phase 6: real use (alongside phase 2; the gate for building more)

- [ ] Sessions become 1-cells and rails become 2-cells, from real recall logs.
- [ ] E1′ runs on real logs, and the result is reported either way.

## 10. Risks

- **Q's meaning turns out wrong for some later use.** `free_certified` says, per cell, wherever F would differ.
- **A wide cell in Hadzihasanovic and Kessler's worst case.** Budgets refuse it, and memory's cells are thin.
- **The port drifts from today's behaviour.** The byte-identical oracle in phase 1 catches it.
- **Building ahead of use,** which the outside reads warned about. Phase 6 runs early, and phase 5 waits on it.
- **The disclosure rule.** The store's descriptions stay off GitHub until its fixes run live on the Pi. The same rule
  applies to anything this plan touches there.
