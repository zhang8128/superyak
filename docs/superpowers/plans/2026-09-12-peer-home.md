# Personal Peer Home Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver a runnable personal home with authenticated accounts, persistent sharing-layer drafts, versioned public/shared releases, private rooms, and verified authenticated exchange between two independently hosted peers.

**Architecture:** Add a small separately installable `peer/` application, leaving existing Engram/Atlas processes and stores unchanged. SQLite owns each peer's users, sessions, spaces, layers, messages and delivery history. FastAPI serves a same-origin browser application; HTTPS with pinned certificates and Ed25519-signed envelopes protects explicitly paired peer exchange. No central registry, hosted account authority, or model API is mandatory. Integrate selected source records through attributed exports rather than importing private live stores.

**Tech Stack:** Python >=3.11, FastAPI, uvicorn, cryptography, SQLite, vanilla HTML/CSS/JavaScript; pytest/httpx and Playwright for tests. Resolve and commit a uv lock in `peer/`. Use standard library scrypt for local password hashing, random hashed session tokens, CSRF tokens and same-origin checks. No CDN resources.

**Spec:** `docs/superpowers/specs/2026-09-12-personal-dashboards-sharing-design.md`; `docs/model-policy.md`.

## Global Constraints

- Personal home across chats, care circles, projects, and organizations is confirmed.
- Open-source and peer-to-peer are requirements. No mandatory global account service, central shared database, or paid model API.
- Only American models may be used; Gemma 4 is acceptable and preferred. No noncompliant fallback. Tests make no unplanned model calls.
- Keep private drafts separate from active shared/public versions. Public means signed-out access to exactly a selected active version.
- A role label, organizational membership, or administrative role does not by itself authorize access to private chats or personal drafts.
- Preserve distinct source/peer identities, corrections and original authorship. A display-name correction must not change grants.
- Existing `.engram/` stores, historical worktrees, Qwen outputs, and Pi services are preserved. The MG worker remains stopped.
- This first application slice uses fictional participants. It does not claim live clinical ingestion, clinical suitability, complete end-user encryption, or measured cluster capacity.
- Use only new `peer/` state directories. Root commands default to `.engram/home`; the demo defaults to `.engram/home-demo` and refuses to overwrite unrelated state.
- Keep files focused. Add modules when a responsibility becomes separate; record the final module/interface map in reports.
- User authorized implementation and continuing integration/push in this session. Do not reopen design approval or ask whether to continue.

## Product and API contract

The application name shown to people is **Superyak**. Main navigation: Home, Chats, My sharing layers, Shared spaces, Connections. Show the person's name, current space, an effective audience label, and a clear saved/draft/active state. Use calm readable typography, responsive layout, keyboard-accessible controls, no icon-only sharing state. User-facing pages explain audiences and content, not database/protocol mechanics. Connection setup may show the technical peer details needed for pairing.

Use JSON API responses with stable `id` fields. Errors return a public-safe message and an appropriate 400/401/403/404/409 status. Store internals and tracebacks never reach the browser. Unless public or authentication routes, require an authenticated local session. Do not trust user IDs supplied as the request's acting identity. One `create_app(data_dir: Path, *, ...)` factory is the integration boundary; it exposes the Store through `app.state.store`. Use per-operation database connections or a properly serialized transaction owner so concurrent browser/worker operations are safe.

Required browser API behavior (implementer may use a consistent equivalent route spelling and must document it for following tasks):

| Route group | Contract |
| --- | --- |
| Session | Login with username/password; server-issued HttpOnly same-site cookie plus CSRF token; `/api/me`; logout revokes the session; login throttling; no public registration default |
| Accounts/invitations | First owner created by CLI; owner can issue expiring, one-use invitations; participant chooses name/password; administrator sees account/setup metadata, never personal content |
| Home | Return current user, their visible spaces, recent accessible chats, own draft/active layers and selected shared items; counts come only from authorized items |
| Spaces | Care-circle/project/organization objects with explicit membership and owner; rename has no grant effect; ordinary users may create their own spaces; no network-wide owner |
| Layers | Create/list/get/save draft with optimistic version check; fields title, body, audience selections, public flag and selected attachment IDs; only owner edits/sees draft |
| Layer release | Activate exact draft version; keep immutable earlier revisions; withdrawal removes active access and creates an ordered withdrawal event; saving another draft leaves current active content unchanged |
| Public | Signed-out route for active public version and explicitly attached files only; no draft, chat, owner account metadata or private citation targets |
| Files | Upload bounded text/PDF/image files into the user's private store; immutable content digest; release only via explicit owned-layer attachment selection; serve as downloads with safe media headers |
| Chats | Create personal/direct/group room using known contacts; list/read/send only for current members; idempotent client message ID; add participants through a linked new room with no old messages; remove participants revokes hosted access and queued delivery |
| Connections | Export/import peer contact cards, review fingerprint and named remote participant, explicit pair/unpair; no automatic discovery or automatic contact merge |
| Sync | Show pending/delivered/withdrawn/failed status; bounded retry of the same signed event; recheck resource grant/version immediately before sending; unavailable peer does not break local editing |
| Assistant | Optional explicit request to approved Gemma using only the current person's selected draft and entered text; disabled until configured and identity checked; generated suggestion stays private until user applies it |

Shared layers can target named users and explicitly selected spaces. A selected organization audience must say that current/future members can see active releases; personal care circles and chats use explicit people. A layer is not automatically shared because it appears under an organization. Effective access summaries show overlapping grant routes. Public access cannot promise exclusion of an individual. Only owned files/content may be republished through this slice.

## Verification and scope audit

The measurable target is the full first application path described above, not all future clinical/HPC integrations. Uploaded files are supported; live medical-record connections require an actual provider and authorization and remain outside this synthetic first slice. Crypto authenticates peer hosts and protects transit; hosting operators can access their local plaintext stores, so do not claim browser-to-browser E2EE. No cluster capacity assumptions, new model downloads, or public disclosure of private history follow from building this product.
