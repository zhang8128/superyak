# The sheaf architecture: what exists, what to build, in what order

Defiant, 2026-11-09, for Andy. **Status: a draft.** No reviewer has read it, and nothing new in it is built. Each
stage becomes its own spec, approved by a fresh reviewer under station law section 3, and every branch merges under
section 2.

**Goal:** one sheaf layer for Superyak that computes something a plain comparison can't, on real data, at a cost a
Raspberry Pi can pay, and that an outside implementer can check against the definitions.

**Why the last part.** Andy, 2026-11-09: mathematics as the connector standard is easier "more from a political than
technical standpoint". Nobody owns a definition, so a county, a hospital or another institute can adopt one without
adopting a vendor. That only works if the definitions are exact and the reference code meets them.

## 0. Where the build stands (2026-11-09)

Built on branch `defiant/sheaf-core`, not yet read by a fresh reviewer and not merged:
- the standard, `docs/standard/sheaf.md`, and 13 known answers worked by hand before any code;
- the reference core, `engram/sheaf_core.py`, and `engram-sheaf check`;
- the native core, `engram/sheaf_kernel.cpp` (C++20, a narrow C ABI, stateless) with its binding
  `engram/sheaf_native.py`, checked against the reference on random sheaves and on arguments no caller should send.

**What the native core is good for today, measured on Defiant:**

| Work | Reference (Python, LAPACK inside numpy) | Native (C++, own Jacobi SVD) |
|---|---|---|
| Counting sections, 14 free nodes of 3 (4.8 million) | 1,910 ms | 13 ms, about 140 times faster |
| Cohomology, 80 unknowns | 51 ms | 11 ms |
| Cohomology, 320 unknowns | 604 ms | 910 ms |
| Cohomology, 480 unknowns | 157 ms | 4,400 ms, about 28 times slower |
| Cohomology, 960 unknowns | answers | refuses: over its work budget |

So the exact, set-valued work belongs in C++ now. For ranks, a hand-written decomposition can't match LAPACK: the
native core's value there is that it is a second, independent implementation that needs only a compiler. A fast
native rank needs a linear-algebra library (LAPACK, Eigen or SuiteSparse), and that dependency is Andy's decision
(section 7). Until then the reference core is the default, and the native one is asked for by name.

**Not done from stage 1:** the permission check's agreement test against `glue_sets`, moving `lighthouse_sheaf.glue`
onto the core, and stage 0's renames. AddressSanitizer has not run: this machine has no sanitizer runtime, so that
test skips here. A build with undefined-behaviour traps and checked containers does run and passes.

## 1. What a sheaf has to have here

A sheaf gives each place some data (its stalk), and gives each step between places a map that carries data across
(its restriction map). Local data that agrees on every overlap glues into one global answer.

- **H⁰** counts the independent global answers: what everyone agrees on.
- **H¹** counts the loops where every pair agrees and no single story fits all of them. Comparing pairs can never see
  these. This is the one thing the sheaf buys, so every stage is tested on it.
- **If every map is the identity, the sheaf sees only the graph's shape, never the data.** The issue #2 audit found
  exactly this in `lighthouse_sheaf.py`. So each use has to say where its maps come from.

one that shows what cohomology buys. The trails are.

## 3. The architecture

Four layers. Each depends only on the ones above it in this list.

```
1. Definitions      docs/standard/sheaf.md            the standard, in words and formulas, with known answers
2. Core             engram/sheaf_core.py              pure mathematics: no storage, no embedder, no network
                    engram/sheaf_kernel.cpp           the same operations natively, behind a narrow C ABI (later)
3. Sheaves          engram/sheaves/permissions.py     adapter over the existing gluing check
                    engram/sheaves/trails.py          maps fitted from sessions, over the n-category
                    engram/sheaves/rail.py            maps fitted between lighthouses
4. Uses             engram-sheaf CLI, the permission check, the trail experiment, the agreement curve
```

### 3.1 Definitions (layer 1)

One document that someone who has never seen this repository can implement from. It states:
- a **base**: a finite graph, optionally with 2-cells (pairs of parallel routes), given as plain lists;
- a **sheaf of vector spaces**: a dimension per node and per edge, and a matrix per (node, edge) incidence;
- a **sheaf of sets**: a finite set per node and edge, and a function per incidence;
- the coboundary δ, H⁰ and H¹, gluing, and holonomy around a 2-cell;
- a **wire format** for all of it (JSON, with matrices as row lists), versioned;
- **known answers**, each a file in the wire format with its expected result.

The known answers are the conformance suite. They are written from the definitions, never from the code:

| Case | Expected (dim H⁰, dim H¹) |
|---|---|
| Any tree, stalk k, identity maps | (k, 0) |
| A cycle, stalk k, identity maps | (k, k) |
| A triangle whose maps compose to a rotation with no fixed vector | (0, 0) |
| K₄, stalk 3, identity maps | (3, 9) |
| Two sections that differ, on one edge | not glued, and the residual names that edge |
| Three sets agreeing in pairs, restriction by intersection | glued, to their union |
| A set-valued triangle with a twist (a cyclic relabelling) | not glued, though every pair agrees |

### 3.2 Core (layer 2)

`engram/sheaf_core.py`, about 400 lines, depending only on numpy and scipy (both already required).

```python
@dataclass(frozen=True)
class Base:
    nodes: tuple[str, ...]
    edges: tuple[tuple[str, str], ...]          # (tail, head), oriented once
    faces: tuple[tuple[tuple[int, ...], tuple[int, ...]], ...] = ()   # 2-cells: two parallel edge paths

@dataclass(frozen=True)
class VectorSheaf:
    base: Base
    node_dim: Mapping[str, int]
    edge_dim: tuple[int, ...]
    maps: Mapping[tuple[str, int], np.ndarray]  # (node, edge index) -> matrix edge_dim x node_dim

def coboundary(F: VectorSheaf) -> scipy.sparse.csr_matrix
def laplacian(F: VectorSheaf) -> scipy.sparse.csr_matrix          # never dense
def cohomology(F: VectorSheaf, tol: float) -> Cohomology          # dim_h0, dim_h1, a basis for H0, the tolerance used
def glue(F: VectorSheaf, local: Mapping[str, np.ndarray]) -> Glued  # the nearest global section, residual per edge
def holonomy(F: VectorSheaf, face: int) -> np.ndarray             # transport one way minus the other
def neighbourhood(F: VectorSheaf, centre: str, radius: int) -> VectorSheaf

class SetSheaf: ...                                                # finite stalks, functions as maps
def glue_sets(F: SetSheaf, local) -> GluedSets                     # exact; refuses past a stated budget
```

Rules the core keeps:
- **Every answer carries its tolerance.** A rank decided by a threshold says which threshold. No silent rounding.
- **Budgets on every call,** in bytes and steps, as the n-category kernel has. Past the budget it refuses.
- **No store, no embedder, no clock.** The same input gives the same output on any machine.
- **dim H¹ comes from the count, not a second solve:** dim H¹ = dim C¹ − dim C⁰ + dim H⁰ when there are no 2-cells.

**The native part.** Start in Python with scipy's sparse solvers. Move the hot loops (building δ, the sparse
products, the block solves) into C++20 beside the n-category kernel once stage 2 shows which ones are hot. Same
pattern as `ncat.py`: a narrow `extern "C"` ABI, `ctypes`, the Python version kept as the oracle. Andy's reason for
C++ applies here too: more will be built on it.

### 3.3 Sheaves (layer 3)

Each adapter turns Superyak's own data into the core's types and says where its maps come from.

| Adapter | Base | Stalk | Maps come from | Asks |
|---|---|---|---|---|
| `permissions.py` | the place DAG | sets of uses (boxes) | intersection | do parents' rules agree at a joint place? (exists today) |
| `trails.py` | one store's n-category, n ≤ 2 | context at a memory, k = 16 to 32 | fitted from the sessions that took each step | are two routes really interchangeable? |
| `rail.py` | the lighthouses and their overlaps | what each holds on a topic, k = 16 to 32 | fitted between stores on consented anchors | what do independent lighthouses agree on, and where do no pairs show the disagreement? |

**What the trails adapter needs from the n-category:** the 0-cells and 1-cell generators of a store, each session as
a composite, and each 2-cell's two boundary paths. All of that is dimension 2 or below, where the kernel is exact and
total today. So this does not wait on the kernel plan's harder decisions, only on the kernel and store reaching main.

**Fitted maps are data, so they are stored.** A new SQLite table per store, written only by the fitting job:
`sheaf_maps(sheaf, node, edge, k, matrix BLOB, n_samples, residual, fitted_at, basis_version)`. A map with too few
samples is not stored; the step is reported as unfitted. The projection to k dimensions is one more stored object
with its own version, since every map depends on it.

### 3.4 Uses (layer 4)

- `engram-sheaf check FILE` runs the core on a wire-format file. This is what an outside implementer compares against.
- The permission check keeps its own fast box algebra, and gains one test that its answers match `glue_sets`.
- The trail experiment and the agreement curve are scripts with pre-registered outcomes, not features.
- Nothing in this plan steers recall. Stages 0 to 3 are observational.

### 3.5 What happens to today's modules

- `engram/sheaf.py` is in live use by compression and reflection, so it keeps working. It is renamed to
  `engram/cohesion.py` with a thin `sheaf.py` shim for one release, and its docstrings say spectral clustering.
- `engram/lighthouse_sheaf.py` keeps its CLI. Its `glue` becomes a call into the core with identity maps, labelled
  as the constant sheaf. The audit's four failing behaviours become tests it must pass (the false-glue pair,
  off-topic uncovered by default, local residuals, energy normalised by the number of stores).

## 5. What it costs

| Operation | Cost | Note |
|---|---|---|
| Build δ | O(E · k²) time and memory | E edges, stalk dimension k; about 24 · E · k² bytes |
| One solver step | O(E · k²) | sparse product |
| dim H⁰ and a basis | O(E · k² · iterations) | iterations grow as the spectral gap shrinks |
| dim H¹ | O(1) after H⁰ | by the count, with no 2-cells |
| Holonomy of one 2-cell | O(p · k³) for paths of p steps | matrix products |
| Adding one use | a rank-k update | no rebuild |
| A query's neighbourhood | O(E_local · k²) | the default on a Pi: never the whole store |
| Fitting one map | O(s · k²) for s sessions on that step, then O(k³) | least squares, or Procrustes |
| Set-valued gluing | fast on tree-like covers, exponential in the worst densely looped case | permissions caps it at 4,096 boxes |

With k = 16 and 10⁷ uses, δ has about 5 × 10⁹ entries (two k × k maps per use), about 60 GB, which is far too
large to hold on a Pi. So global cohomology of
a whole store is out of reach there, and stage 2 works on neighbourhoods and on samples. That limit goes in the spec.

## 6. Risks

- **The maps turn out to be the identity, or noise.** Then the sheaf adds nothing over comparison. Stage 2's
  controls are there to find that out early.
- **Too few sessions per step to fit a map.** Most steps are taken once. Pool steps by topic, and report how many
  steps had enough data.
- **Numerical rank is a judgement.** A tolerance decides dim H⁰ on real data. Every result states it, and the
  experiment reports how the answer moves across a range of tolerances.
- **Agreement that is really shared lineage.** Stage 3 counts copies once and shows the control curve.
- **Building ahead of use,** which both outside reads warned about. Stages 0 and 1 are cheap, and 2 and 3 are
  experiments with gates, not features.
