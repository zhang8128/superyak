# Independent Stampede implementation review

Reviewed the uncommitted implementation against the September 12 launch spec and plan. This is a code/process-boundary review, not a Stampede3 or Intel inference validation. No remote submission or inference was performed.

## Important findings and disposition

1. **P1: Hardware acceptance did not exercise the experiment's structured response contract.** The original `cluster.py` startup requested a plain word; `provider.py` requested unconstrained text while `experiment.py:_validate_output` required a bare JSON object. An otherwise healthy Qwen backend could pass startup and fail every campaign turn on JSON fences/prose. **Fixed during review:** current `provider.py:62` requests `response_format={"type":"json_object"}`; `cluster.py:181` now sends a synthetic experiment packet, validates answer/memory/publication, and requires publication action `none` before backend acceptance. The pinned llama.cpp [server interface](https://github.com/ggml-org/llama.cpp/blob/3057bb66c86c46d5781e50e85462a760ba7d1feb/tools/server/README.md) supports JSON response format and disabling thinking through chat template parameters.

2. **P2: Automatic fallback could mix backend precision within comparisons or resumed cells.** `profiles.py:244` uses vLLM bfloat16 while `profiles.py:252` launches a converted float16 GGUF through SYCL. Originally each node chose independently, and cell identity recorded neither backend nor resolved model revision. **Fixed during review:** `cluster.py:170` accepts one campaign backend identity under an exclusive lock; workers retain its revision/precision, use the resolved model revision, and reject incompatible execution identities. This fixes a measurable source of confounding rather than merely adding labels.

3. **P2: Fetching live checkpoint directories could produce an unusable history archive.** The original `launcher.py:fetch` tarred `cells` with `--ignore-failed-read` while `experiment.py:_checkpoint` advanced `CURRENT` and deleted older generations. Tar could enumerate generations, then archive a newer `CURRENT` naming a generation absent from the archive; vanished files could be silently omitted. **Fixed and re-reviewed:** `experiment.py:104` takes `snapshot.lock` around generation mutation; `export.py:84` takes that same lock while reading CURRENT, verifying and copying the nominated generation, and checking copied hashes. `launcher.py:fetch` downloads a unique completed archive and sidecar, verifies their digests, then replaces the local artifact. An independent actual-SQLite export/extract/restore check preserved a completed turn and made only the five remaining calls.

4. **P2: Serial references received less evidence than the population comparisons.** Original `experiment.py:359-360` selected `cohort == i % 2` for every kind. With serial population one, `bench-log` and `firmware-note` could never be exposed, confounding single-agent comparisons with withheld evidence. **Fixed and re-reviewed:** `experiment.py:367` gives serial references both cohorts at the original rounds while population members retain partitioned exposure. The real experiment regression passed. Documentation correctly describes one-member sharing as self-publication.

5. **P1: A killed job could remain reported as healthy indefinitely.** The first status revision rejected reports from previous job IDs but still trusted a persisted current-job `running`/`hardware_verified` report without consulting Slurm. A batch SIGKILL or node failure could leave that report behind after the job terminated. **Fixed and re-reviewed:** `launcher.py:738` scheduler-confirms verified running reports. Terminal failure overrides the report to failed, terminal completion remains incomplete until campaign completion is known, and unknown scheduler state becomes unverified. The regression with a stale running report and `NODE_FAIL` passed.

No additional critical or important defect was established in the inspected ownership, model HTTP deadline, source isolation, SQLite backup, independent-probe cleanup, or bounded model-server command paths. Incomplete responses and absent usage remain explicitly auditable. Host oneAPI/driver compatibility, real inference latency, capacity, and shared-filesystem behavior remain unverified.

## Final follow-up review

All five established findings above are resolved in the reviewed implementation. No unresolved critical or important finding remains from this review.

- Coordinated the final review boundary with the launcher owner after export, generation resume, and stale-job status changes were ready. Inspected explicit terminal-state gating, per-generation submission markers, preservation of original inputs, rejection of old-job completion, archive hash verification, and export source exclusions.
- Re-reviewed cluster failure handling: handled node failures persist a job-scoped failed report and exit zero so MPI does not abort unrelated nodes. The batch controller requires a successful launcher exit and all current-job node reports completed before reporting success. Live summaries refresh while nodes run; old-job reports cannot establish hardware verification. Actual model calls and startup diagnostics receive the configured seed.
- Independently ran the ten targeted final regressions for coherent exports, corrupt-generation refusal, serial evidence, snapshot locking, persisted worker failure, stale/current-job aggregation, live verification, and stale-running scheduler override: **10 passed in 11.03 seconds**.
- Independently performed export restoration using real Engram Storage: initial status `interrupted`, one completed turn; exported one cell; extracted into a fresh directory; restored two agent stores; final status `complete`, six completed turns, **exactly five new calls**.
- Read `docs/stampede3-deployment.md`, the Stampede README section, Makefile targets, and `scripts/Start Stampede3.command`. No material unsupported claim found. The guide explicitly states the one-device serving baseline, finite community lifetime, unequal token/experience budgets, synthetic-only ingestion, retained audit logs, and unverified Intel/TACC runtime. It distinguishes per-cell consistent snapshots from unsynchronized log observations and requires off-cluster backups.
