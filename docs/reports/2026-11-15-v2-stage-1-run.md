# v2 stage 1: the first run with model workers

Serenity, 2026-11-15 (UTC). Task 11 of `docs/superpowers/plans/2026-11-14-v2-stage-1-room.md`. One run on one
Mac: three items, two model workers. The sample is three, so nothing here is a rate.

**Three items, three turns, three passed verified on the first attempt, in 25 minutes.** Twenty of those
minutes were one turn waiting on a test run that could not finish in its sandbox. That was a fault in the
room's own tests. The run found it; seven readings of the source had not.

## What was run

- **The room:** `yak` built from a8a6127c of branch `v2`, the commit CI passed on Ubuntu x86-64 and on macOS.
  The machine is macOS 27.0.1 on arm64. The items' base is 453c8b6b, which adds only the checks.
- **The command:** `yak clock run --once-through --worker claude:opus --worker codex:gpt-6.1-sol`, stdin
  closed, default limits: 20 minutes a turn, three attempts an item, 15 minutes a check.
- **The workers:** Claude Code 2.1.325 with the model alias `opus`, and codex-cli 0.163.0 with `gpt-6.1-sol`.
  Each runs inside its own program's sandbox, with the network it needs to reach its model. The room's jail
  is for the checks and for the room's own git in a worker's tree.
- **The items' repository:** a clone of the `v2` branch alone, 15 MB. It held that branch and three wrong
  commits, and nothing else.

## Before the run

- **Each check was shown able to pass.** When the room freezes a check it measures that the check fails on
  the base and fails on a wrong commit. It does not measure that the check can pass, and a check that cannot
  pass says nothing about a worker. So each writer supplied a reference fix as a patch. A script worker
  applied it in a separate copy of the repository, and each check passed in the jail.
- **Each check was read by the other family.** The lead, a Claude session, read the two Codex-written checks.
  A Codex reader read the Claude-written one and found two wrong fixes that would have passed it: a count in
  UTF-16 units, and a rule that refuses only a title of exactly 201 letters. One case was added for each, and
  each was then shown to fail its broken fix.
- **Two rehearsals on a throwaway repository,** because no model worker had run under the clock before: a
  trivial shell item and a small Rust fault for each worker. Four items, four turns, four passed verified, in
  34 and 47 seconds.
- **A dress rehearsal of the launch itself,** with a script worker in the model workers' place.

## What the run found

**1. Two of the clock's tests never end where a clock cannot look at processes.**

Turn 3's worker ran `cargo test -p yak -p turn` in its own sandbox. Its copy of the clock's test program
was still running eleven minutes later, when the turn's limit ended it.

- **Why.** Two tests run a clock that waits for work with no end of its own. A helper stops it: one once a
  worker's record appears, the other once the clock says its daily ceiling is reached. Inside a worker's
  sandbox a clock cannot inspect processes, so no check is frozen and no turn starts. The helper never acts,
  nothing stops the clock, and the test waits for ever.
- **Reproduced outside any sandbox,** with a `ps` that fails first on the path: of the clock's 38 tests, 12
  pass, 24 fail, and 2 do not end in four minutes. They are those two: `stop_ends_a_running_worker` and
  `in_forever_the_ceiling_waits_and_says_so_once`.
- **Fixed.** Each of the two tests now owns a stop: its room is stopped at a limit of two minutes unless
  the test is over first, and the test then fails where it asserts. A new test runs each of the two with a
  `ps` that fails and asks that it ends. With the fix, the same reproduction ends by itself in 122 seconds
  with nothing left running.
- **Who should have found it.** The seventh reader named this kind of fault in one test, a helper that waited
  without limit. The lead fixed that one and did not look for its like. A test that starts something with no
  end of its own has to own a stop that acts on every path, its own failure included.

**2. The room judged the work, not how the turn ended.** Turn 3's worker committed in the first minutes of
its turn, then ran two crates' whole test suites, and that run never came back. At twenty minutes the room
ended it and judged the commit that was there. The frozen check passed on it, twice. A room that failed
every timed-out turn would have thrown away a correct fix and spent a second turn on it.

**3. A worker cannot run the tests that judge the room itself.** Inside a worker's sandbox the clock cannot
inspect processes and no jail can be entered. Turn 1's own commit message says seven command-line tests
fail there with and without its change. A worker that changes shared code cannot see whether it broke the
clock. The frozen check is what stands between such a change and the branch, and the check is about the
item, not about the rest. Here the lead ran the whole suite on the merged tree afterwards.

**4. Codex cannot commit, so its commit says nothing.** Its sandbox keeps `.git` read-only (measured
directly: `git commit` fails there on `index.lock`). The room commits on its behalf, with a fixed message.
The prompt tells every worker to commit, so Codex spends a step on a commit that must fail, on every turn.
Claude's commits carry an account of what was done and why; Codex's carry none.

**5. What the store cannot say.** It keeps no text of a turn, on purpose. It does keep each step's kind,
whether it touched a tracked file, and whether it succeeded. It has token counts for Claude's turns (254,923
and 425,925 in) and none for Codex's. It cannot say what a failed step was: the two above are named from
separate measurements, not from the record.

**6. A sandbox copies every object of the item's repository.** A turn's clone is made from the whole
repository: every branch, and objects no branch reaches. So a reference fix, or any unpublished branch,
that sits in the item's repository is in every worker's clone. This run used a repository cloned from one
branch. The room does not enforce that.

**7. The room does not measure that a check can pass.** See "Before the run". The measurement was made by
hand here, with a script worker and a patch.

**8. Reading a check across families was cheap and found two real gaps.** Both were wrong fixes that passed.
Neither the check's writer, with eleven broken fixes of its own, nor the lead had seen them.

A third reader, the ship Tardis, read two of the checks from the public branch once they were frozen, by
reading only. It called both sound and left two notes. The checks find items by the layout of `yak item
list`, one `"id":` to a line, so a worker who tidied that output unasked would have failed for no real
reason. And an empty `--wrong` value is tested neither way.

**9. Smaller things.**
- `sqlite3 -readonly` cannot open a room's store once its clock has exited, since the store is in WAL mode.
  `yak status` can. The numbers here were read from a copy.
- A worker's clone holds every check in the repository, not only its own. Nothing went wrong from it.
- The workers found how to build offline by reading the check's script: the prompt gives a title, the
  check's command and the rules, and no word about the toolchain.

## Added the same day: the failure that was not explained

CI's run on the commit that carried this report failed on macOS in one test, `workers_take_turns`: the one
named above. This time it printed what the clock had done, because the lead had made it do so after losing
the first failure's output.

**It was not a flaky test. The room had failed a correct turn.** The fourth turn was judged failed with "its
clone was not usable: inspect git metadata: No such file or directory". The item was given out again and
passed, so the workers' order was not the one the test expects.

**Why.** When a worker has ended, the room walks every path under the clone's `.git` to confirm it holds only
plain files and directories. It lists a directory, then looks at each entry. An entry that was listed and is
gone when it is looked at made the walk fail.

**What moves under it, measured on macOS 27 with git 2.54:**

| Probe | Result |
| --- | --- |
| What a commit starts | `git maintenance run --auto --quiet --detach`, every time |
| A quiet machine, 80 commits, watched from a second thread | Its lock file appears in all 80. Nothing is left once the commit has returned |
| Under load, 8 processes of 250 commits, walking `.git` the moment each commit returns | A directory under `objects/` listed and then gone, in about 7% of commits |
| The same, with git's automatic tidying off | Nothing gone in 2,000 commits |

Git's own tidying, started by the worker's commit, is still packing loose objects and removing their
directories after the commit has returned.

**Two changes.**

- A sandbox's clone has git's automatic tidying off. A test reads git's own trace of a commit there, beside
  an ordinary repository where the same git does start it.
- The inspection starts again when a listed path has gone, up to five times, and then refuses in a sentence
  that names the path. A path going away means something is still changing the clone, and then nothing seen
  so far confirms anything.

**Not known.** In that reproduction entries went only once about a hundred loose objects had piled up, and
the clones in the two failures were small. So what had gone in those two is not shown. The first change may
not be what they needed. The second covers whatever moved, and names it if it keeps moving. A room of 160
trivial turns under load, run with the old program, failed none: the fault is rarer at that level than the
reproduction can show in a few minutes.

**What it cost.** A correct turn judged failed and tried again, twice in some forty full runs of a
four-turn test. Three such failures on one item would have given the item up.
